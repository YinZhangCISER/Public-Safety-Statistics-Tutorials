# Module Template and Style Guide

*Developed by Yin Zhang, PhD, Assistant Professor, Data Analytics Program, Department of Mathematics and Statistics, Washington State University, for the Washington Data Exchange for Public Safety (WADEPS) through the Center for Interdisciplinary Statistical Education and Research (CISER).*

Every module in this repository follows one of the three templates below. The templates exist so that a reader who finishes one module already knows how to read the next one, and so that anyone adding a module produces something that matches.

---

## Shared rules

**Length.** Beginner modules are a five minute read. Intermediate modules are eight to twelve minutes plus a notebook. Advanced modules are fifteen to twenty minutes plus a notebook.

**Every concept arrives through a public safety question, never through a definition.** The first sentence of a module is a question someone would actually ask about public safety data. The method appears only after the question has been made to matter.

**Write from outside the agency, not inside it.** The audience includes residents, reporters, council members, students and researchers as well as officers and agency staff, so a module never assumes the reader works in a department. Do not write "our numbers", "our agency", or "how did we do". Write "a department reports", "the agency's rate", "what does that number tell you". Where a scene needs a person in it, name several: a commander, a reporter, a council member. The one exception is dialogue, where an outside speaker may of course say "our city".

**One dataset.** Every example uses the synthetic WADEPS dataset in [Data/](../Data/). Never introduce a new dataset for one example.

**Say what the method cannot do.** Every module has a Pitfalls section. A module that only explains when a method works has taught half of it.

**Plain language first, notation second.** Where a formula appears, the sentence after it says the same thing in words.

**Figures.** Every module has at least one figure. Figures are PNG files in the level's `Figures/` folder, generated by the module's notebook or by `Figures/make_figures.py`, committed to the repository so they render on GitHub without running anything.

**Cross references.** Link back to the module a concept came from and forward to the module that builds on it. Use relative paths so the links survive a move to another GitHub organization.

**Attribution.** Every module opens with the byline block below and closes with the provenance note. The name and affiliation appear exactly once per module, at the top.

**Punctuation.** Do not use the hyphen or dash as prose punctuation. Write "year over year", not the hyphenated form. Dashes are fine inside code, inside file names, and inside official WADEPS category labels, which are reproduced exactly as published.

## Template A. Beginner module

No formulas. No code. No jargon that has not been defined on the page.

```markdown
[byline block]

## The Core Concept
Two or three sentences. Plain language only.

## Why It Matters
The cost of getting this wrong, told as something that happens to a real
organization: a program cancelled too early, a crisis declared that was not
one, a budget moved to the wrong precinct.

## The Example
A small table, five rows or fewer, drawn from the teaching dataset. Then a
figure. Then what the figure shows, in words.

## What To Watch For
Two or three short bullets. The specific ways this idea gets misused.

## 💡 The Insight
One sentence, set apart. The thing worth remembering a year from now.

## Check Your Understanding
Two questions, each with the answer folded away:

<details><summary>Question 1 text</summary>
Answer, with the reasoning, not just the result.
</details>

## Key Takeaway
One sentence, imperative voice. What the reader should now do differently.

[footer block]
```

## Template B. Intermediate module

Light notation, always translated. One notebook.

```markdown
[byline block]

## The Question
The operational question, stated concretely enough to have a numeric answer.

## The Idea in Plain Language
The method, explained before any symbol appears.

## The Method
The formula or procedure, followed immediately by the same statement in
words. Then the assumptions, listed plainly.

## Worked Example
Real numbers from the teaching dataset, small enough to follow by hand,
with a figure. The reader should be able to reproduce the first step on
paper.

## Do It Yourself
> 📓 **Notebook:** [Module_NN_Title.ipynb](Notebooks/Module_NN_Title.ipynb)
> [Open in Colab badge]
> About 20 cells, 15 minutes.

What the notebook covers, in three or four bullets.

## Pitfalls
A table: what goes wrong, what it looks like in the output, what to do.

## Check Your Understanding
Three questions in folded blocks, at least one of which asks the reader to
interpret a number rather than compute one.

## Key Takeaway

[footer block]
```

## Template C. Advanced module

Full notation. Diagnostics are mandatory, not optional. One notebook with complete code.

```markdown
[byline block]

## The Question
Framed as a research or analytic decision, not a calculation.

## Model and Assumptions
The model written out, each term named in words. The assumptions stated as
a numbered list, each one paired with the diagnostic that tests it and the
consequence of it failing.

## Estimation
What is being estimated and how. Identification before computation.

## Worked Example
The full analysis on the teaching dataset, including the diagnostic output
and its interpretation, not only the coefficient table.

## Recovering the Planted Answer
What the estimate should be, from [GROUND_TRUTH.md](../../Data/GROUND_TRUTH.md),
what the model returns, and whether the interval covers the truth. Where a
simpler method gets it wrong, show that too, with the number.

## Diagnostics
The checks that must be run before the result is reported, each with the
output that would make you abandon the model.

## Do It Yourself
> 📓 **Notebook:** [Module_NN_Title.ipynb](Notebooks/Module_NN_Title.ipynb)

## When Not To Use This
The conditions under which a reader should reach for a different module.

## Reporting the Result
One short paragraph of the kind a reader could paste into a memo, with the
caveats that have to travel with it.

## Further Reading
Three to five references, standard textbooks and accessible papers only.

[footer block]
```

## Notebook rules

1. **Runs top to bottom in Google Colab with no local setup.** Data are read from the repository's raw GitHub URL, declared once in the first cell.
2. **Every code cell is preceded by a markdown cell** saying what it does and why, in the same plain language as the module text.
3. **No cell longer than about 20 lines.** Split it.
4. **Compatible with pandas 1.4 and pandas 2.x.** Avoid API that exists in only one. Do not use `DataFrame.append`. Prefer `pd.PeriodIndex` over frequency strings that changed spelling.
5. **Outputs are cleared before committing**, except figures that the markdown file links to.
6. **Ends with a short exercise** whose solution is in a folded cell at the bottom.
7. **Same byline** in the first markdown cell and the last.
